# Parity harness

The Kotlin core is a **port** of the Python one, not a rewrite. This directory
holds the mechanism that proves the port is faithful, because reading 1200
lines of Kotlin twice is not a verification method.

## The idea

The Windows repo (`darts-coach-windows`) is the specification. It has 300+
passing tests. The Kotlin port must produce *identical* output for identical
input.

So the harness runs the Python implementation and the Kotlin implementation over
the same corpus and compares the results byte for byte.

```
darts-coach-windows/          dart-coach-android/
  src/game/parser.py     -->   core/.../Parser.kt
  src/game/darts.py      -->   core/.../Darts.kt
  src/game/state.py      -->   core/.../GameState.kt
        |                          |
        |  tools/parity_gen.py     |  core/src/test/.../ParityTest.kt
        +------> corpus/*.json <---+
```

## Corpus format

One JSON file per area, in `corpus/`. Generated from the Python side, checked
in, and consumed by both.

### `corpus/parser.json`

```json
[
  {
    "id": "bare-number",
    "text": "125",
    "state": {"remaining": 501, "turns_played": 0},
    "expect": {
      "command": "turn_score",
      "score": 125,
      "darts": null,
      "double": null,
      "refused": false,
      "needs_confirmation": false
    }
  },
  {
    "id": "one-eighteen-ambiguity",
    "text": "one eighteen",
    "state": {"remaining": 501, "turns_played": 0},
    "expect": {
      "command": "turn_score",
      "score": 118,
      "darts": null,
      "double": null,
      "refused": false,
      "needs_confirmation": false
    }
  }
]
```

The `one eighteen` case is not arbitrary. It is the rule that the second
number must be 20 or more for "one eighty" to mean 180 - see the comment in
`src/game/parser.py` and `PLAN.md` Phase 1. It is the single most likely
thing to get subtly wrong in a port, so it is pinned explicitly.

### `corpus/plans.json`

```json
[
  {
    "id": "plan-170",
    "remaining": 170,
    "preferred_double": null,
    "expect": {
      "labels": ["T20", "T20", "Bull"],
      "leaves": 0,
      "finishes": true,
      "fallback_labels": [],
      "fallback_leaves": 170,
      "doubles": [],
      "speak": "treble twenty, treble twenty and double bull",
      "display_lines": ["T20 T20 Bull", "to win"]
    }
  }
]
```

`plans.json` covers every remaining score from 1 to 501. The search is
deterministic, so this is a complete characterisation, not a sample.

### `corpus/routes.json`

The same shape, but with `preferred_double` set and `expect` holding a route
instead of a plan. `expect` is `null` when the Python planner found no shot at
that double - the Kotlin one must not invent one.

```json
[
  {
    "id": "route-170-d20",
    "remaining": 170,
    "preferred_double": 20,
    "expect": {
      "labels": ["T20", "T20", "D20"],
      "leaves": 0,
      "finishes": true,
      "fallback_labels": [],
      "fallback_leaves": 170,
      "speak": "treble twenty, treble twenty and double twenty",
      "display_lines": ["T20 T20 D20", "to win"],
      "double": 20
    }
  }
]
```

`routes.json` has 6513 cases and 1561 distinct behaviours among them.

### `corpus/state.json`

Turn-by-turn sequences, so the state machine is checked over a whole leg
rather than one operation at a time:

```json
[
  {
    "id": "full-leg",
    "turns": [45, 26, 60, 0, 100, 41, 20],
    "expect": {
      "remaining": 209,
      "turns_played": 7,
      "preferred_double": null
    }
  }
]
```

## Running it

Generate the corpus from the Python repo:

```
cd ../darts-coach-windows
python tools/parity_gen.py --out ../dart-coach-android/corpus
```

Run the Kotlin side:

```
./gradlew :core:test --tests '*ParityTest*'
```

The Kotlin test reads the checked-in corpus, runs each case, and asserts the
result matches. A mismatch fails the build with the offending case id.

## What parity does not cover

Parity proves the *logic* is the same. It says nothing about:

- Whether the transcription is accurate on the device (Phase 1 spike).
- Whether the echo gate holds on the phone (Phase 4).
- Whether the timing of the half-duplex gate feels right.

Those are measured on the device, not against the Python.

### The commands that are Android-only

Two commands exist in the Kotlin core and not in the Python one:

| Command | What it does | Where it is written down |
|---|---|---|
| `whats_the_leave` | Answers "what would that leave", for a player looking at the board rather than the phone. | `docs/GATE-AND-BARGE-IN.md`, the change that added it. |
| `report_miss` | Corrects the last dart in the turn after a miss, and re-plans the darts that are left. | `docs/MISSED-TARGET.md`. |

They are not in the corpus, because the corpus is generated by running the
Python parser, and the Python parser has no such commands. The Python
`parser.py` has no `report_miss` and no `whats_the_leave` at all.

**This is a deliberate choice, not an oversight.** The Windows coach is a
working product and must not be disturbed, and adding `report_miss` to it
would mean adding the whole correction state machine to its `main.py` - the
parser command is the small part of it. The gain would be parity on a
feature the Windows build does not have, for a user who never sees the
Windows build.

The cost is honest and worth stating: these two commands are only pinned by
the Kotlin tests. `MissedTargetTest` and `MissedTargetBoardTest` are the
specification for `report_miss`, in the same way the corpus is the
specification for everything else. If the behaviour of the correction
changes deliberately, those tests change with it, and there is no Python
side to compare against.

**What would change this.** If the Windows coach is ever given the same
command, the corpus can be extended to cover it, exactly as it covers
everything else. The Kotlin side would then need no change at all, because
the command names and the parse results are the same shape the corpus
already carries.
